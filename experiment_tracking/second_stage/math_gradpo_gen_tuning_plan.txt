Fixed fast settings
-------------------
C=7 requested new replacements per region, plus the unchanged candidate.
B=5 beam survivors and at most five final beam prompts.
G=200 correctness-balanced gradient subset (up to 100 correct + 100 incorrect).
F=0.5 instruction-only fluency penalty.
Random training pool=1600 per source prompt; seed=42.
Target reasoning output limit=4096 for training/source inference and validation.
Candidate-generation and beam-synthesis output limits remain 10000.
Validation unchanged: deterministic 3 x 300 from the existing 3 x 500 file.
Stable-score lambda=1; no test runs.

Dual backend on the same logical GPU: vLLM ratio=0.50, HF device=cuda:0.
Raised from 0.40 at the user's request after reducing target output to 4096.
The first attempt exhausted GPU memory with ratio 0.50 and gradient batch 2.
HF used 37.39 GiB and the vLLM worker used 41.64 GiB on the 79.10 GiB GPU.
The user approved gradient batch 1, retaining ratio 0.50 for the restart.
Use re_prompt_optimization_vllm_v2 (vLLM 0.11.0).
vLLM generates text, evaluates validation, and forward-scores gold-answer
loss plus instruction fluency. HF retains gradients and gradient-dependent
token-probability/ranking operations.
Gradient microbatch=1; HF selection batch=4; vLLM objective submission=128.
HF selection batch does not control vLLM's dynamically scheduled GPU batch.
If gradients still run out of memory, consider reducing the vLLM ratio to
0.40, not G or validation size. Batch 1 has not yet been GPU-tested here.
The failed attempt saved all 1600 responses and the 200 balanced examples
(available: 1234 correct, 366 incorrect; selected: 100 each). The restart
can reuse its matching response/subset cache. Beam search never started,
so the remaining seven attempts were not run by the failed shell job.
No new four-parameter vLLM safeguards were enabled by these command edits.
No input length-sorting feature is added.

Exact prompt objectives are already reused within one fixed beam search,
including unchanged survivors and repeated synthesized text. No new cache
implementation was necessary. Bounded submission batches handle all newly
needed candidate/example pairs together, rather than one-example HF scoring.
Synthesis stays greedy with the existing prompt tags and no new fallback.
Gold-answer loss remains conditioned on cached model reasoning, averaged
within answers and then equally across examples. Reasoning is not supervised
as a gold trace. The fixed answer instruction remains uneditable.

Cost and preparation caveats
-----------------------------
With C=7 plus unchanged, at most 8 expansions occur at the first region and
5 x 8 = 40 per later region, before exact-prompt deduplication and score reuse.
Final validation can generate up to 5 x 900 = 4500 responses per attempt
plus an uncached source evaluation (previously up to 10 x 900 = 9000).
The 4096 cap reduces worst-case generation/context length but may lower scores.
Do not guarantee a full-pipeline speedup from the small Qwen scorer benchmark.
Keep actual region/candidate counts, bucket sizes, parsing failures, raw/stable
gains, token usage, and phase timings in the existing artifacts. Dedicated
edit_tracking remains disabled.

Older Math full-matrix generator/scripts still refer to old Qwen RPO sources
and duplicate original EvoPrompt snapshots. Do not run them as this plan;
update sources/settings after selecting the final tuning configuration.
