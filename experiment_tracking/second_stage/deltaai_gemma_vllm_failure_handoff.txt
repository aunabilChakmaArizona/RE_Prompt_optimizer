DELTA AI GEMMA/VLLM MATH GRADPO FAILURE HANDOFF
================================================

Date audited: 2026-09-21
Purpose: handoff for a Codex instance running on DeltaAI to reproduce, isolate,
and fix the abnormal Gemma-3-4B vLLM behavior before any Gemma MATH-500
second-stage results are used.


BOTTOM LINE
-----------

The eight Gemma MATH-500 GradPO-Gen tuning commands completed without a Python
traceback or GPU out-of-memory error, but the resulting experiments are not
scientifically usable. The DeltaAI vLLM engine silently generated corrupted
Gemma completions.

Two separate failure signatures occurred:

1. RPO5 source: source validation was plausible, but GradPO replacement-candidate
   generation returned multilingual/repetitive garbage. Parsing therefore kept
   only each original span. All four RPO5 attempts were no-op searches and
   retained the source prompt.

2. RPO10 source: source validation itself collapsed to 1/900 correct. Almost
   every generation reached the 4,096-token cap, and most decoded responses were
   empty or whitespace. This corrupted source result was saved in the shared
   source-validation cache and reused by the later RPO10 attempts. The apparent
   42-62% candidate scores therefore are not valid improvements over the source.

Do not report any of these eight runs. Do not rerun the full eight-run matrix
until a small exact-prompt smoke test passes.

RPO5 FAILURE EVIDENCE
---------------------

The first RPO5 candidate-generation output begins with unrelated mixed-language
tokens and then repeats empty Markdown code fences for thousands of characters,
for example:

  "อกาส folyam ioninost ... <返回值 ... ``` ... ``` ..."

The parser found no valid replacement list. Each selected region therefore had
only its original text as its candidate, for example:

- " following math problem" -> " following math problem"
- " for rotations" -> " for rotations"
- " diagrams" -> " diagrams"
- "Solve" -> "Solve"
- " manageable steps" -> " manageable steps"

Consequently, the beam search had no actual edits to test. The four unchanged
RPO5 scores must not be interpreted as evidence that GradPO could not improve
the prompt; the candidate-generation model call failed semantically.

Do not delete user artifacts during diagnosis. Use fresh debug cache roots, or
use --refresh-source-validation-cache and --refresh-gradient-cache only after
the runtime fix is verified.

Important cache-design gap: source_validation_cache.py and gradient_cache.py
include the generation library version, model, prompt, records, seed, and
decoding settings in their identities. They do not currently include
disable_image_inputs, enforce_eager, prefix-caching configuration, other vLLM
engine settings, or hardware architecture. Therefore an image-enabled or
conservative-engine rerun can incorrectly reuse a cache made under the failing
image-disabled/default-engine configuration. This identity should be audited
and likely extended.


WHAT IS ALREADY RULED OUT OR UNLIKELY
-------------------------------------

- Wrong source prompt: archive hashes match the intended files exactly.
- Answer grader/parser: the raw model text is already empty or corrupt.
- Merely an answer-tag problem: no coherent reasoning exists in most failed
  source outputs.
- The 4,096-token cap as the root cause: corruption begins immediately; the cap
  only stops the loop. Raising it would likely waste more compute.
- Dual vLLM/HF GPU-memory competition: the corrupted RPO5 candidate output was
  produced by vLLM before the HF model needed for later scoring was resident.
- Gradient code: HF gradient collection completed successfully. The observed
  failure is in vLLM text generation/source validation.
- Normal process warnings: the destroy_process_group NCCL warning occurs during
  vLLM shutdown and is not the cause of semantically corrupt output.


CURRENT WORKING HYPOTHESIS
--------------------------

This resembles a Gemma-3/vLLM runtime-generation bug or unsupported execution
combination rather than a GradPO algorithm error. The strongest suspects are:

1. Gemma-3 multimodal handling with limit_mm_per_prompt={"image": 0} in vLLM
   0.11.0 on the GH200/aarch64 path.
2. vLLM V1 prefix caching with Gemma-3.
3. torch.compile/CUDA-graph behavior on GH200/aarch64.
4. A combination of the above rather than any one setting alone.

This is a hypothesis, not a confirmed root cause. Relevant upstream reports
with similar symptoms include:

- https://github.com/vllm-project/vllm/issues/14817
  Gemma-3 empty outputs while generating until the length limit.
- https://github.com/vllm-project/vllm/issues/20341
  Gemma-3 no output or repeated output while other model families work.
- https://github.com/vllm-project/vllm/issues/18733
  Gemma-3-4B output dominated by special/padding tokens.
- https://github.com/vllm-project/vllm/issues/39389
  Gemma-3 output changes/non-determinism associated with V1 prefix caching.

4. Build a minimal exact-prompt diagnostic that prints, for every completion:

   - finish_reason
   - number of completion token IDs
   - first and last completion token IDs
   - tokenizer.decode(..., skip_special_tokens=True)
   - tokenizer.decode(..., skip_special_tokens=False)

   This is necessary because ordinary decoding can hide thousands of padding,
   image, or other special tokens and make a long completion appear empty.

5. Use the exact same prompt, seed, SamplingParams, and model revision in an A/B
   matrix. Change one engine setting at a time:

   A. images allowed; otherwise default vLLM settings
   B. images disabled; otherwise default vLLM settings
   C. images allowed; enable_prefix_caching=False
   D. images allowed; enforce_eager=True
   E. images allowed; both prefix caching disabled and eager execution enabled
   F. Transformers generation control

   Do not initially combine all changes, because doing so cannot identify the
   actual cause. The production --vllm-conservative-settings flag combines eager
   execution, disabled prefix caching, max_num_batched_tokens=4096, and
   max_num_seqs=128; it is useful only after isolated tests.

6. Test two exact prompt types:

   - The RPO5 candidate_meta_prompt saved in region_candidates.json. This is a
     particularly cheap and strong reproduction because a single optimizer call
     produced obvious garbage; batching is not required to expose the symptom.
   - The RPO10 source prompt on 10-20 validation examples. If this works singly,
     repeat as one vLLM batch to test whether the failure is batching-related.

7. Verify prompt rendering independently:

   - Compare HF and vLLM tokenizers/model revisions.
   - Save the exact apply_chat_template text and token IDs.
   - Confirm the fixed answer instruction occurs exactly once before generation.
   - Confirm the question associated with each returned output is unchanged.

8. Interpret the A/B outcome:

   - Images allowed works, images disabled fails:
     remove --vllm-disable-images for Gemma-3 and extend cache identities.
   - Default fails, prefix-cache-off works:
     disable prefix caching for Gemma-3 and extend cache identities.
   - Default fails, eager works:
     suspect compile/CUDA graphs; use eager mode for Gemma-3 on DeltaAI.
   - Every vLLM mode fails but Transformers works:
     treat this as a vLLM 0.11/GH200 runtime incompatibility and do not use vLLM
     Gemma generation/scoring until a compatible version is established.
   - Both vLLM and Transformers fail:
     inspect model weights/revision, tokenizer/chat template, and the exact
     rendered prompt rather than GradPO.
   - All minimal tests pass but the full run fails:
     investigate large-batch output mapping, engine reuse, and cache loading.

9. Only after one RPO5 candidate-generation smoke test and one RPO10 source
   validation smoke test produce coherent outputs should the complete matrix be
   relaunched. Use fresh CODE values and fresh cache roots or explicitly refresh
   both caches. Preserve the failed artifacts for comparison.


EARLIER DELTA AI FAILURES ALREADY FIXED IN THE CURRENT CODE
-----------------------------------------------------------

These are separate from the silent generation corruption but useful context:

1. Hugging Face 401 gated-repository error:
   fixed by authenticating and setting HF_TOKEN for Gemma access.

2. "Gold answer target was not found after chat-template rendering":
   fixed by locating/replacing the answer-tag content and using the appended
   fixed-answer sentence only when an answer block is absent.

3. "vLLM returned a non-finite scoring logprob" during prompt-fluency scoring:
   fixed by using vLLM only for expensive candidate task loss and the already
   loaded HF model for the five short candidate-prompt fluency scores.

The final archived eight-run job passed these earlier failure points. Its
remaining problem is silent, semantically corrupted Gemma generation.


ACCEPTANCE CRITERIA BEFORE FULL RERUN
-------------------------------------

- RPO5 candidate generation returns parseable, task-relevant replacement lists.
- RPO10 direct validation produces coherent reasoning rather than empty/special
  token output.
- RPO10 source accuracy is in the expected broad range, not approximately 0%.
- Answer tags appear normally.
- Exact source score is regenerated under the chosen engine configuration.
- Cache metadata distinguishes that engine configuration from the failed one.
- One small GradPO run completes with real replacement candidates and sensible
  source-versus-final validation comparison.
